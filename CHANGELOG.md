## [v0.74.0](https://github.com/kagura-ai/memory-cloud/releases/tag/v0.74.0) — 2026-09-22

Tool guardrails: a memory marked with `details.tool_trigger` reaches the model at the matching tool call — as the reason for a denied call, or as context next to its result — through Claude Code plugin hooks, Codex plugin hooks, and server-side digests for MCP clients that run no hooks. Also on the MCP surface: a failed `tools/call` now carries `isError`.

### Added
- **Tool guardrails — the server contract** ([#1619](https://github.com/kagura-ai/memory-cloud/issues/1619)): a memory becomes a guardrail by carrying `details.tool_trigger = {tool, on?, match?, action?}` — `tool` is a regex full-matched against the tool name the client reports (`Bash|PowerShell`, `mcp__.*__remember`, `Edit|Write`), `on` is `pre` (default) or `result`, `match` an unanchored regex over the call's input or result text, `action` is `inform` (default) or `block` (`block` needs `on: "pre"` and a `match` that names a literal). Both patterns are validated on every write against a safe-regex grammar — the subset that behaves the same in Python `re` and JavaScript `RegExp`, with no backreferences, lookaround, named or atomic groups, nested quantifiers or ambiguous unbounded runs; a stable `regex_*` / `tool_trigger_*` code names the violated rule. The server compiles a pattern once to validate it and never runs it: **matching happens only in the client.** The new deterministic read — MCP `load_guardrails(context_id, cap?)` and REST `POST /api/v1/memory/guardrails` — returns the trusted-tier pinned set and the tool-triggered set as two independently capped lanes, with a `format: 1` payload and a per-credential `version` hash that every client caches; connector-ingested rows and contexts whose `trust_tier` is not `trusted` are never served, ingest strips `tool_trigger`, and Sleep never merges, archives or re-scores a guardrail. Adding, changing or removing `tool_trigger` — and any edit or delete of a memory that already carries one — needs **context editor or above** and a user credential (`permission_denied` with `required_role: "editor"` on MCP, `403` on REST; an agent-bound key gets `tool_trigger_requires_user_credential`); `forget` keeps its silent contract and skips a guardrail the caller may not delete. Contract: [Tool guardrails](docs/mcp-tools.md#tool-guardrails).
- **Claude Code plugin hooks** ([#1619](https://github.com/kagura-ai/memory-cloud/issues/1619)): the `kagura-memory` plugin declares hooks (`claude-hooks/hooks.json`) that run one stdlib Python script behind a POSIX `sh` guard. `SessionStart` calls `load_guardrails` once over the configured MCP URL, caches the set under the plugin's data directory (`guardrails/<context_id>.json`, mode `0600`), adds one line to Claude's context (how many guardrails are active) and shows the user a one-line notice naming new, changed or removed guardrails (`(by another member)` for someone else's); with the server down a cache up to 24 h old is used. `PreToolUse` / `PostToolUse` / `PostToolUseFailure` match locally against the cache — no network, tool inputs never leave the machine: `inform` arrives as `additionalContext` next to the tool result, `block` denies the call once with the memory summary as the reason (a deny costs one model turn), each guardrail once per session and agent; `/clear` and `/compact` reset the main thread. A `remember` / `update_memory` / `forget` call refreshes the set in the background. Credentials come only from the plugin's `userConfig` (`server_url`, `api_key`, `context_id`, `max_action` = `block` | `inform`); `.mcp.json`, `~/.claude.json`, project settings and `KAGURA_*` variables are never read, and `python3` is resolved to a path outside the project. Needs `python3` 3.9+ on `PATH`; Windows is unsupported for these hooks. Put `guardrails=off` in the `.mcp.json` URL's query (`?guardrails=off`, or `&guardrails=off` when the URL already has one, such as `?profile=core`) so the server does not also send a digest. Setup: "Claude Code Plugin › Tool guardrails (hooks)" in [MCP Client Setup](docs/mcp-clients.md).
- **Codex plugin hooks** ([#1620](https://github.com/kagura-ai/memory-cloud/issues/1620)): the Codex plugin (`plugins/kagura-memory`) gains `hooks/hooks.json` and a Codex adapter for the same script (`--client codex`), so Codex CLI and the ChatGPT desktop app's local Codex runtime receive guardrails at the matching tool call from the same cache, matcher and renderer: `SessionStart`, `PreToolUse` / `PostToolUse` on every tool, and one async refresh on `remember` / `update_memory` / `forget`. `Bash` is matched on its command, `apply_patch` as `Edit` / `Write` with one subject per file header, any other tool on its compact JSON input; the deny reason never repeats the command (Codex appends it). Settings (`context_id`, `max_action`, `mcp_server`) live in `${PLUGIN_DATA}/config.json`; credentials are read from the user's own `[mcp_servers.<name>]` table in `$CODEX_HOME/config.toml` — `url` plus exactly one Authorization source (`bearer_token_env_var`, `env_http_headers.Authorization` or `http_headers.Authorization`); anything else is one `SessionStart` notice naming the field and zero requests. Only `SessionStart` and the refresh ever read `config.toml` or open a socket; tool events read the cache alone. Reading `config.toml` needs Python 3.11+ (`tomllib`); on an older interpreter `SessionStart` prints one notice and tool events keep running from the cache. Codex lists the four hook entries as untrusted until you accept them once in `/hooks`; the file is byte-pinned by a test so that every change to it — which sends every user back through `/hooks` — is deliberate.
- **Guardrails for MCP clients without tool hooks** ([#1621](https://github.com/kagura-ai/memory-cloud/issues/1621)): ChatGPT web, Claude Desktop / Claude Chat, Codex cloud tasks and most other MCP clients run no hooks, so a guardrail reached their model only if the model happened to recall it. The server now renders the same trusted-only, binding-filtered tool-triggered set (`load_guardrails.tool_triggered`) on the three model-visible lanes those clients have. **Server `instructions`** — `initialize` and `server/discover` return the base text plus a digest of one context's guardrails (up to 5 entries, one line each, 1,200 characters at most; the first 512 always hold the header and the whole first entry) when the endpoint URL selects it, `…/mcp/w/{workspace_id}?guardrails=<context_id>` (same query as `?profile=`), or, with the parameter absent, when the credential is an agent-bound key with a default or sole binding. **`get_context_info(context_id).guardrails`** — on by default: `{items: [{memory_id, summary, importance, authored_by_caller, source_type}], total_available, truncated, tool_triggered_version}`, up to 10 entries; the session-start skills fold it in after `load_pinned`. **Export block** — `GET /api/v1/memory/guardrails/digest?context_id=<uuid>` returns an `AGENTS.md` block (`text/markdown`, up to 20 entries) for a Codex cloud setup script — the documented recipe writes it between two marker lines and keeps it out of the task's diff — and `&target=instructions` previews exactly what the `instructions` lane serves the calling credential. One switch: `?guardrails=off` turns both server lanes off (the setting for a client whose plugin hooks already deliver guardrails); a value that is neither `off` nor a context id is ignored and never folded into `off`. Every lane is fail-open: a denied, unknown or external-tier context, an empty set, a database error or the digest budget expiring all serve the base text, and the handshake never fails. Summaries only — never `content`, `details`, tags or patterns. Rules: [Server instructions](docs/mcp-tools.md#server-instructions); per client: [MCP Client Setup](docs/mcp-clients.md).

### Changed
- **The MCP server's `instructions` text is reworded and is now returned by `initialize` too** ([#1621](https://github.com/kagura-ai/memory-cloud/issues/1621)): the base text points a client to `get_context_info(context_id)` for a context's rules and guardrails before `remember` / `recall` / `explore`; before this release only `server/discover` carried `instructions`. With no `guardrails=` selection and no agent-bound key, `server/discover` keeps its public one-hour cache hints and is byte-identical for every caller; whenever a selection was attempted (any `guardrails=` value, including `off`, or an agent-bound key) the result is `cacheScope: "private"` for 5 minutes, whatever the outcome — a denied caller and an allowed one never share a cache entry. `tools/list` is untouched.
- **The dev `docker-compose.yml` publishes the data stores on loopback only** ([#1626](https://github.com/kagura-ai/memory-cloud/issues/1626)): PostgreSQL 5432, Qdrant 6333 / 6334, Redis 6379 and MinIO 9000 / 9001 are published as `${COMPOSE_BIND_HOST:-127.0.0.1}:PORT:PORT` instead of on every interface — in that file Redis and Qdrant run without authentication, PostgreSQL uses the `.env.example` password, and Docker's `nat` rules run ahead of a host firewall. The API (8080) and web (3000) entries and the production compose files under `terraform/single-server/` are unchanged; a new bats guard in the CI `shell` job rejects any tracked compose file that publishes a data-store port without a loopback default. `docs/getting-started.md` gains "Reaching the data stores" (`docker compose exec`, `ssh -L`, the `COMPOSE_BIND_HOST` override, an IPv6 and a WSL2 note).

### Fixed
- **Failed tool calls are flagged with `isError: true`** ([#1622](https://github.com/kagura-ai/memory-cloud/issues/1622)): both MCP transports serialised a tool error as a plain successful `CallToolResult`, so a client could not tell a failed `tools/call` from a successful one without parsing the private `{"status": "error", …}` envelope, and hook runners keyed on `isError` (Claude Code's `PostToolUseFailure`) never fired. Every error envelope — `unknown_tool`, `invalid_context_id_format`, `context_id_required`, a permission error, a handler exception — now carries `isError: true`; `content` is byte-identical to before, success results carry no `isError` key, and JSON-RPC protocol errors are unchanged. Described in `docs/api-surface-1.0/error-responses.md`.
- **The tag near-duplicate hint fired on compound tags** ([#1617](https://github.com/kagura-ai/memory-cloud/issues/1617)): `session-cookie` next to `session`, `cache-layer-redis` next to `cache-layer`, `session-2026-09-11` next to `session` — a topic and a sub-topic, not two spellings of one tag — and, because the generic tag usually has the highest count, the false hint masked the real mechanical variant (`session_cookie`). The write lint now skips a pair where one tag's segments (split on whitespace, `_`, `-`, `/`, `:`, `#`; not `.`, so `node` / `node.js` still hints) are a whole-segment prefix of the other's, and picks an equal-fold match (`session_cookie`) ahead of the most-used one. Numbered tags keep the v0.73.1 rule (`session-2026-09` / `session-2026-09-21` stay related). The read path is unchanged: a narrower or broader stored tag stays a valid `suggest_tags` answer for an empty tag-filtered `recall`.
- **The External Keys page had no sidebar entry with BYOK off** ([#1616](https://github.com/kagura-ai/memory-cloud/issues/1616)): with `ENABLE_BYOK=false` the page is still the workspace owner's console for keys stored before the flag was turned off (list / toggle / delete answer; only create / update return `404`), and in the default `RESOLVE_STORED_BYOK_KEYS=true` posture those keys are still in use — but the sidebar dropped the entry on the flag alone, so the page was reachable only by typing its URL. The entry now shows for the workspace **owner** when `features.byok` is on **or** the workspace already stores at least one key (one owner-only list probe per workspace per page load, only on a BYOK-off deployment), and stays hidden while either answer is pending. No backend or API change.
- **The Codex CLI setup snippets failed to load on current Codex** ([#1624](https://github.com/kagura-ai/memory-cloud/issues/1624)): the manual `~/.codex/config.toml` entry set an inline `bearer_token`, which Codex rejects for a streamable-HTTP server (`bearer_token is not supported for streamable_http`) and which makes the whole `config.toml` fail to load, plus a `type = "http"` key Codex does not know; the recommended `codex plugin install` is not a subcommand; and the Web UI's Codex tab rendered the same two defects with the API key embedded in the file. Docs, the Web UI Codex tab and the plugin `SKILL.md` now agree on `codex mcp add kagura-memory --url "<url>" --bearer-token-env-var KAGURA_API_KEY`, with a two-key `[mcp_servers.kagura-memory]` (`url`, `bearer_token_env_var`) as the manual form — the key stays out of the file — checked against Codex `rust-v0.155.1`. `docs/troubleshooting.md` gains an entry keyed to the error above, and a guard test parses every published TOML snippet against Codex's key allowlist.

### Notes
- **Migration:** `alembic upgrade head` — `e84_1619_tool_guardrails`: adds the partial index `idx_memories_tool_trigger` on `memories` (built `CONCURRENTLY`, no table lock; re-runnable after a mid-build failure) and admits `load_guardrails` to the `memory_access_events` operation CHECK (swapped `NOT VALID`, then `VALIDATE`, so audit writes continue). Reversible: downgrade drops the index and restores the previous CHECK while keeping the audit rows.
- **New env knobs** (all optional): `GUARDRAIL_LOAD_CAP` (default `50` — cap on the tool-triggered lane of `load_guardrails`, kept separate from the pinned lane's cap so a large pinned set cannot crowd the guardrails out), `MCP_GUARDRAIL_DIGEST_ENABLED` (default `true` — the `instructions` lane only; `get_context_info.guardrails` and the export route stay served) and `MCP_GUARDRAIL_DIGEST_TIMEOUT_MS` (default `500` — the budget for the one database read on `initialize` / `server/discover`; on expiry the base text is served).
- **MCP surface:** 63 → 64 tools (`load_guardrails`, listed after `load_pinned`; exempt from rate limiting; not part of `?profile=core`). The full tool list measures 83,486 characters, within the 84,000 budget the size-guard tests pin. New REST routes `POST /api/v1/memory/guardrails` and `GET /api/v1/memory/guardrails/digest`. New validation codes `tool_trigger_*` / `regex_*` (the stable `<code>` token inside `invalid details.tool_trigger: <code>: <sentence>`), `permission_denied` with `required_role: "editor"` on guardrail writes, and the audit operation `load_guardrails` in `memory_access_events`.
- **Plugins:** the Claude Code and Codex plugin manifests are bumped in lockstep. The Claude Code plugin now declares `hooks` and a `userConfig` — Claude Code asks for `server_url`, `api_key` (stored as a sensitive value), `context_id` and `max_action` (default `block`) when the plugin is enabled (`/plugin` → kagura-memory → configure), or takes them from `claude plugin install … --config key=value`; with nothing configured the hooks are silent. The Codex plugin declares `hooks`, which Codex lists as untrusted until accepted in `/hooks`. A client whose plugin hooks deliver guardrails should carry `guardrails=off` in its MCP URL's query (`?guardrails=off`, or `&guardrails=off` after an existing query) so the server does not deliver the same guardrails a second time.
- **Dev environment:** after this release the dev data stores answer on `127.0.0.1` only. A setup that reached PostgreSQL / Qdrant / Redis / MinIO from another machine sets `COMPOSE_BIND_HOST` (shell or project `.env`) or uses an SSH port-forward to the host's loopback; anyone using `docker-compose.yml` as a deployment file with remote `psql` / Qdrant access has the same two options or moves to `terraform/single-server`. Production compose is unchanged.
- **Developer tooling:** the Bash `PreToolUse` reminder hook in `.claude/settings.json` now reaches the model — it returns `hookSpecificOutput.additionalContext` on stdout (stderr at exit 0 is debug-log only), fires on `gh pr create` alone, and reads its stdin without `echo`, which under `dash` broke the JSON for any multi-line command ([#1623](https://github.com/kagura-ai/memory-cloud/issues/1623)); the `/release` skill is rewritten for the PR-based flow used since v0.70.0 (release branch → PR → squash → annotated tag → GitHub Release → milestone close), with a lockstep test over the seven version files and the CHANGELOG heading ([#1625](https://github.com/kagura-ai/memory-cloud/issues/1625)); four places documented the version endpoint as `GET /api/v1/info` — it is `GET /api/v1/system/info` ([#1618](https://github.com/kagura-ai/memory-cloud/pull/1618)).

## [v0.73.1](https://github.com/kagura-ai/memory-cloud/releases/tag/v0.73.1) — 2026-09-21

Follow-ups to the token-economy release, plus a credential that could not be withdrawn.

### Changed
- **The core tool profile is offered wherever the endpoint URL is shown** ([#1609](https://github.com/kagura-ai/memory-cloud/issues/1609)): the web UI's MCP config block has a switch, "Core tools only (smaller tool list)" (default off) — when on, every rendered and copied URL carries `?profile=core`. README, `docs/getting-started.md` and the per-client sections of `docs/mcp-clients.md` show both URLs with one wording; `docs/troubleshooting.md` gains "A tool I expect is missing from my client". The server default is unchanged (all tools).
- **`GET /api/v1/external-keys` items carry `is_protected`** ([#1613](https://github.com/kagura-ai/memory-cloud/issues/1613)) (also on the create / update / toggle responses; additive). The External Keys page shows the Required badge and locks delete / disable only when it is true.

### Fixed
- **`OPENAI_API_KEY` could never be deleted or disabled** ([#1613](https://github.com/kagura-ai/memory-cloud/issues/1613)), even on a deployment whose embeddings do not use OpenAI or that no longer reads stored keys, so an owner could not withdraw their own credential. It is now protected only while `ENABLE_BYOK` and `RESOLVE_STORED_BYOK_KEYS` are on **and** OpenAI embeddings are in use — `EMBEDDING_PROVIDER=openai`, or a live context of the workspace routes to an OpenAI embedding model. Delete and disable share the rule (the disable guard also follows the row's provider, since the embedding service picks the stored key by provider). Refusals keep status `400` and their shape; the message states the actual reason. With `ENABLE_BYOK=false` the owner's list / toggle / delete paths were already reachable — stored keys can now be withdrawn through them.
- **The tag near-duplicate hint fired on numbered tags** ([#1608](https://github.com/kagura-ai/memory-cloud/issues/1608)): `issue:#1599` "resembled" `issue:#179`, `v0.73.0` resembled `v0.69.0`, `session-2026-09-21` resembled `session-2026-05-20` — false hints on almost every write in a workspace that tags by issue, version or date, and the same noise in `tag_suggestions` on an empty tag-filtered `recall`. Two tags of the same shape whose numbers differ in value are no longer related; the same number written two ways (`sprint-07` / `sprint-7`, full-width digits) still is, and so are abbreviations and typos (`dev-env` / `dev-environment`, `kuberentes` / `kubernetes`).

### Notes
- No migration, no new environment variables, no operator action.

## [v0.73.0](https://github.com/kagura-ai/memory-cloud/releases/tag/v0.73.0) — 2026-09-21

Token economy of the MCP surface. Everything a tool returns — and the tool list itself — is paid for in the calling model's context window; this release removes the avoidable part. Several response shapes change: read **Changed** before upgrading a client that parses tool results.

### Added
- **Tool profiles** ([#1601](https://github.com/kagura-ai/memory-cloud/issues/1601)): the endpoint URL in a client's local MCP config can select which tools `tools/list` returns — `…/mcp/w/{workspace_id}?profile=core` (the 12 memory / context tools) or `?tools=remember,recall,reference` (explicit allowlist, wins over `profile`). No parameter, or `profile=full`, is byte-for-byte the previous list, on both the session-based and the stateless (2026-07-28) transports. An unknown profile, or an allowlist that matches no known tool, is a JSON-RPC `-32602` naming the valid values; unknown names inside an allowlist are ignored. The profile is a **view, not an authorization boundary**: `tools/call` never reads it and keeps its role checks. See [Tool Profiles](docs/mcp-tools.md#tool-profiles) and the per-client examples in `docs/mcp-clients.md`.
- **`list_contexts(name_contains=…)`** ([#1600](https://github.com/kagura-ai/memory-cloud/issues/1600)): case-insensitive substring filter, applied after the permission-scoped list; plus `include_summary` (summary truncated to 300 characters, `summary_truncated` flags a cut) and `include_details` (the previous per-item shape). The envelope gains `total` (contexts in the response).
- **`recall_upcoming(include_details=true)`** ([#1599](https://github.com/kagura-ai/memory-cloud/issues/1599)) returns the full `details` per item, as before this release.

### Changed
- **Tool results are compact UTF-8 JSON** ([#1599](https://github.com/kagura-ai/memory-cloud/issues/1599)): non-ASCII text (Japanese, for instance) arrives as-is instead of as 6-character `\uXXXX` escapes, and separators carry no spaces. Any JSON parser reads both forms identically; only a client matching raw substrings such as `"status": "success"` would notice. The JSON-RPC transport body is unchanged.
- **`recall`** ([#1599](https://github.com/kagura-ai/memory-cloud/issues/1599)): `related_tags[]` entries are `{tag, count}` — `sample_summary` repeated, in full, a summary already present in `results[]`. Result items **omit** `context_summary`, `superseded_by`, `contradicts` and `supersede_candidate` when empty (treat an absent key as "none"), and `score` is rounded to 4 decimals. MCP surface only: REST `/memory/recall` and the web UI are unchanged.
- **`recall_upcoming`** ([#1599](https://github.com/kagura-ai/memory-cloud/issues/1599)): default items are `{memory_id, summary, type, trigger}` (`trigger` = `details.trigger`). `get_agent_bootstrap`'s upcoming component — MCP tool and REST companion — ships the same lean row.
- **`list_contexts` is a slim name → id directory by default** ([#1600](https://github.com/kagura-ai/memory-cloud/issues/1600)): items are `{id, name, is_private, is_locked, last_used_at}` (+ `memory_count` with `include_stats`). `summary` and `embedding_model` moved behind `include_summary` / `include_details`; for one context's full details call `get_context_info(context_id)`. Plugin skills use the new default.
- **Tool descriptions are trimmed to a token budget** ([#1602](https://github.com/kagura-ai/memory-cloud/issues/1602)): descriptions and parameter descriptions keep what an agent needs to call a tool correctly (purpose, when to use it instead of a neighbour, parameter semantics, response keys, the security rule on writes, the supersede workflow, trusted-tier guidance); tutorials and rationale moved to the new **Usage notes** section of `docs/mcp-tools.md` and to the `guide` / `recall` / `remember` skills. Schema structure is unchanged and pinned by a skeleton snapshot test; budgets are pinned by tests.

### Fixed
- **`list_contexts` could be rejected by the client** ([#1600](https://github.com/kagura-ai/memory-cloud/issues/1600)): with a few dozen contexts the response (every summary, escaped) grew large enough for an MCP client with a tool-result limit to refuse it, which broke the first step of every plugin skill.
- **A non-UTF-8 query string can no longer raise in the legacy session-id lookup** ([#1601](https://github.com/kagura-ai/memory-cloud/issues/1601)).

### Notes
- Measured on the fixtures pinned by the new size-guard tests: a k=5 `recall` 22,779 → 4,553 characters; `list_contexts` with 40 contexts 488,842 → 6,455; `tools/list` for all 63 tools 110,608 → 81,834 characters, and 28,254 with `?profile=core`. The `recall` fixture is mostly Japanese; for ASCII-only content the encoding change is neutral and the saving comes from the removed duplication.
- No migration, no new environment variables, no operator action. The Claude Code / Codex plugin manifests are bumped in lockstep; update the plugin to pick up the skills written for the slim `list_contexts`.

## [v0.72.0](https://github.com/kagura-ai/memory-cloud/releases/tag/v0.72.0) — 2026-09-20

Closed-beta invites after first real use: the invitee lands in the app instead of back on the login form, and the inviter can tell links apart, resend one, and read an honest count.

### Added
- **A label per invite** ([#1595](https://github.com/kagura-ai/memory-cloud/issues/1595)): `POST /api/v1/beta-invites` takes an optional JSON body `{"label": string | null}` (free text, up to 100 characters after trimming; control characters and text that is not valid Unicode are a `422`). A request with no body behaves exactly as before. The label is stored on the invite, returned on every list item and on the created payload, and rendered on the row. It is inviter-private: it never reaches a log line, an audit row or an error message, and it is deleted with the inviter's account.
- **One-click reissue** ([#1595](https://github.com/kagura-ai/memory-cloud/issues/1595)): `POST /api/v1/beta-invites/{id}/reissue` (session only, no body, `201`, same payload as create) revokes an `active` or `expired` invite and mints a replacement with the same label in one transaction — for a recipient who lost the link, since only the token's hash is stored and the URL cannot be shown again. Errors: `404` (unknown id or someone else's invite), `409 BETA-INVITE-002` (already used), new `409 BETA-INVITE-003` (`details.reason = "already_revoked"` — a double-click cannot mint a second link), `409 BETA-INVITE-001` when an expired invite is reissued at the cap (the revoke is rolled back). The audit log records one `beta_invite.revoked` and one `beta_invite.created` row that cross-reference the two invites by id. The dialog shows a Reissue button on active and expired rows and presents the new URL in the same one-time panel.
- **The inviter sees who an invite admitted** ([#1595](https://github.com/kagura-ai/memory-cloud/issues/1595)): a `redeemed` item in `GET /api/v1/beta-invites/me` carries `redeemed_email`, the admitted account's current e-mail. It is read from the live account only — never from the allowlist snapshot — so it becomes `null` when that account is erased. This deliberately replaces the v0.70.0 "status only" contract: the inviter is the person who vouched for the invitee.

### Changed
- **The invite header is a breakdown, not a bare "Used N"** ([#1595](https://github.com/kagura-ai/memory-cloud/issues/1595)): `GET /api/v1/beta-invites/me` gains `active` and `redeemed` (`active + redeemed == used` by construction; `used` / `remaining` / `quota` are unchanged), and the dialog reads `Active 2 · Used 1 · Limit 4` / `有効 2 · 使用済み 1 · 上限 4` (`No limit` / `上限なし` for a system admin). The old figure counted slots in use, so one redemption plus two unused links read as "3".

### Fixed
- **An invitee no longer lands on the login form after signing up** ([#1594](https://github.com/kagura-ai/memory-cloud/issues/1594)): `/join/[token]` now returns to `/workspace/dashboard` after the OAuth round trip. Before, it returned to `/`, which redirects to `/login`, which ignored the session that had just been created — and a second sign-in from there invalidated it.
- **`/login` forwards a visitor who is already signed in** ([#1594](https://github.com/kagura-ai/memory-cloud/issues/1594)): to the sanitized `return_to`, default `/workspace/dashboard`, without rendering the form. `?error=…` and `?cancelled=1` still render their banners (an `email_in_use` error can arrive while another account's session is live). The page shows a labelled spinner until the session check settles and renders the form after 3 seconds regardless, so a slow or failing `/auth/me` cannot lock anyone out.

Operational hygiene for the single-server template: bounded container logs, and proxy logs that never hold an invite token.

### Fixed
- **Container logs are bounded** ([#1591](https://github.com/kagura-ai/memory-cloud/issues/1591)): every service in `terraform/single-server/docker-compose.app.yml`, `docker-compose.prod.yml`, `docker-compose.data.yml` and `docker-compose.ollama.yml` declares `logging: json-file` with `max-size: 50m` / `max-file: 3` through a per-file `x-logging` anchor. - **The Caddy template scrubs invite tokens from its logs** ([#1591](https://github.com/kagura-ai/memory-cloud/issues/1591)): `Caddyfile.tpl` logs through a `filter` encoder that replaces the token slot of `/join/<token>`, `/beta-invites/<token>/preview` and `invite=<token>` with `REDACTED` in `request>uri` and in the `Location` / `Refresh` response headers (a trailing-slash redirect echoes the path), and drops the `Referer`, `Cookie`, `Next-Url` and `Next-Router-State-Tree` request headers. The same scrub is applied to Caddy's **default logger**: when an upstream is down, Caddy writes a second `http.log.error` line about the request to stderr with the full URI and headers, so filtering the access log alone left a copy of the token in the same container log. Ordinary URIs are logged unchanged.

### Notes
- **Applying to a running stack:** re-render the Caddyfile and reload Caddy for the log format (no recreate needed). For rotation, run `docker compose … up -d --force-recreate caddy web` once — the API colours are recreated by every `deploy.sh` run; recreating a container also discards its old oversized log file; `postgres` / `qdrant` / `redis` restart when recreated, so do that in a maintenance window. A host-level `daemon.json` with the same limits remains a good default.
- **Caddy 2.6.2+** is required for the response-header redaction (an older 2.x image silently skips it; the URI rewrite and the header deletes still work) — `docker compose pull caddy`.
- No application code, API, migration or environment-variable change. With this template the proxy-log precondition for `ENABLE_BETA_INVITES` (see v0.70.0) is met out of the box; if you run a different proxy, replicate the scrub for both its access log and its error log. See Deployment → *Container log rotation* and *Closed-beta invite links*.
- Two new bats suites (static pins, and a live suite against `caddy:2-alpine` including the 502 path) run in the CI `shell` job.

## Historical development notes (pre-v0.16.0)

### Added
- **Embedded LanceDB vector backend — "Kagura Lite" (preview)**: a feature-flagged, in-process vector store for single-process self-hosted / CLI / desktop / edge deployments that want to avoid running a separate Qdrant server. Set `KAGURA_VECTOR_BACKEND=lance` (default `qdrant` is unchanged — the new path is a single `is None` branch in `db/qdrant.py`, zero behavior change for the server). New `db/vector_store.py` introduces a `VectorStore` Protocol + cached backend selector; `db/lance_store.py` implements `LanceVectorStore`. Japanese stays owned by the existing Sudachi pipeline (lemmas + readings + synonym/hiragana augmentation) feeding a weighted `search_text` FTS column, so recall behavior matches the Qdrant path without relying on LanceDB's native CJK tokenizer; hybrid 60/40 fusion stays in `services/search_service.py`. Isolation is a single-quote-escaped, UUID-validated SQL pre-filter (`build_lance_filter`). LanceDB is an **optional** dependency (`pip install '.[lite]'`) — the default install is unchanged. **Preview limitations**: `copy_context_points`, cross-collection GDPR `delete_user_points`, and the admin BM25-drift scroll raise `NotImplementedError` under this backend; the server (multi-process + nightly Sleep writer) deployment should stay on Qdrant since LanceDB writes are single-process. Unit-tested: backend selector + the security-critical filter/escaping builder (LanceDB-independent). **Post-merge hardening (max code-review follow-up):** semantic search now sets `.metric("cosine")` explicitly (LanceDB defaulted to L2 → wrong/negative similarity scores that broke confidence/absence detection); all writes serialized under the store lock (LanceDB is single-writer even in-process); embedding dimension tracked per-collection (multi-model variants no longer collide); date-range filters normalized to canonical UTC (offset-aware, validated); FTS + scalar indexes rebuilt lazily after the first write; importance-range consistency validated (4xx parity with Qdrant); reads/deletes on a not-yet-created collection return empty instead of erroring.
- **Slot-based owned-workspace cap (epic #674)**: User-level workspace ownership is now gated by `cap = 1 (base) + users.workspace_slot_bonus`, decoupling the cap from workspace plan tier (FREE/BASIC/PRO). The two axes are now orthogonal — `workspace.plan` controls feature limits (memory / api), `users.workspace_slot_bonus` controls how many workspaces a user may own. **Phase 1 ship breakdown:**
  - **Data model + cap rewrite** (#675 sub-A): alembic `e15_675_workspace_slot_bonus` adds `users.workspace_slot_bonus INTEGER NOT NULL DEFAULT 0` with a `>= 0` CHECK constraint. `QuotaService.check_workspace_creation_allowed` switched from highest-tier derivation to `BASE_CAP + bonus`. `PlanTier.max_owned_workspaces` field removed.
  - **Admin inc/dec UI** (#676 sub-B, supersedes #667): new `PATCH /api/v1/admin/users/{user_id}/workspace_slot_bonus` endpoint (atomic `UPDATE ... RETURNING` for race safety, DB CHECK as safety net, `BONUS-002` structured 400 for would-be-negative requests, audit log on every mutation, `reason` required only when the new cap would drop below current owned_count). The full detail route `/admin/users/{user_id}` surfaces the bonus value with `+1` / `−1` buttons.
  - **TOCTOU + enforce flip** (#677 sub-C): `QuotaService._acquire_workspace_create_lock` uses `pg_advisory_xact_lock(hashtextextended('workspace_create:' || user_id, 0))` (64-bit hash, per-user serialization, released on transaction commit, zero contention with other paths). The 64-bit `hashtextextended` was deliberately chosen over 32-bit `hashtext` to push birthday-paradox collisions from ~65k users out to ~2³² users (PR #686 loop 4 review). The `ENFORCE_WORKSPACE_CAP` flag flips warn-only → deny + `QuotaExceededError` 4xx. Production `memory.kagura-ai.com` flipped to `true` on 2026-05-17 (rollback runbook: `docs/ops/workspace-cap-rollback.md`).
  - **Cap visibility on admin list** (#695): `/admin/users` list response gains `owned_count` / `workspace_slot_bonus` / `base_cap` / `cap` per user (additive — mirrors `WorkspaceSummary` field names from the detail endpoint, so client code and mental models stay consistent across closely-related admin endpoints). The list page renders a new "Cap" column with at-cap emphasis and a bonus-inclusive tooltip.
  - **Tiers docs update** (#664): admin `/plans` "Tiers" tab no longer surfaces a `max_owned_workspaces` column (the value was removed from `PlanTier`).

  **Migration safety**: the grandfather migration uses `EXCLUSIVE TABLE LOCK` on `users` for the brief window of `UPDATE users SET workspace_slot_bonus = GREATEST(0, owned_count - 1)` — existing PRO users with N owned workspaces keep their effective cap (bonus = N − 1). **Idempotent**: re-running the migration converges to the same value (`GREATEST(0, count - 1)`).

  **Self-hosted operators**: `terraform/single-server/.env.prod.example` documents `ENFORCE_WORKSPACE_CAP=true` as the recommended default once log-only observation confirms no false-positive denials. The rollback runbook documents service-name-explicit `--force-recreate` recovery without redeploy.

  **Phase 2 follow-up (not in this release)**: Stripe "workspace slot" product / webhook-driven bonus increment / dangling-workspace handling. The Phase 1 model is intentionally local-only; the Phase 2 design will upgrade `workspace_slot_bonus` from a raw column to a SUM cache backed by `UserSlotPurchase` rows so the addon pattern (#485 storage_limit etc.) carries through cleanly.

### Documentation
- **R2 ChecksumSHA256 binding default-flip criteria documented** (#577): Extended `docs/ops/r2-checksum-binding-rollout.md` with §10 "Default flip & flag removal criteria" that codifies the upstream-maintainer-facing conditions for flipping `R2_CHECKSUM_BINDING_ENABLED` default from `false` to `true` (acceptance #2) and for eventually removing the flag entirely (acceptance #3). Criteria are structured across three observability axes: [A] upstream SDK availability + PyPI age (always observable), [B] hosted SDK-distribution telemetry on `memory.kagura-ai.com` covering BOTH REST `/api/v1/files/reserve` and MCP `init_file_upload`, and [C] self-hosted release-window heuristic on inbound 403 bug reports. [B] is **gated on a User-Agent capture prerequisite** that is not yet implemented — both REST and MCP currently drop `User-Agent` (§9 Future Work #1), so §10.1 [B] is documented as not-yet-evaluable until that capture lands and a 7-day observation window passes. The §10 criteria are distinct from §3 Step 3, which targets individual self-hosted operators making their own flip decisions. Also resolved the SDK version placeholder that was deferred during the #556 rollout: `kagura-memory-python-sdk v0.14.0` shipped 2026-05-11 (kagura-ai/kagura-memory-python-sdk#97), so the runbook (§3 Step 2, §4.2 example output, §8 Q3, §保守注記) and `backend/src/config/settings.py:r2_checksum_binding_enabled` docstring now reference `>= 0.14.0` instead of the original `>= 0.4.0` placeholder. **No backend behavior change** — flag default remains `false`. Acceptance #2 (flip the default) and #3 (remove the flag) remain tracked under #577 for future PRs once §10.1 / §10.2 criteria are met.

## [v0.16.0](https://github.com/kagura-ai/memory-cloud/releases/tag/v0.16.0) — 2026-05-13

Pre-1.0 Hardening release: SQLAlchemy 2.0 `Mapped[T]` migration (PR-A/B/C of #370), domain-exception refactor across PermissionService / SystemAdminService / handle_update_context (#401, #603, #604), DCR scope narrowing to exclude `memory:admin` (#608), zero-base-tier defense-in-depth across all `effective_*_limit` paths (#569), CI guards for ORM↔migration drift (#587) and `Mapped[T]` (#370), alembic head merge fix for safe production rollout (#632). 20 issues closed in this milestone.

### Added
- **Body sha256 binding on presigned PUT (Phase 1.5)** (#556): `R2Storage.generate_presigned_put` now plumbs the reserved `sha256` through to R2's S3 Object Integrity feature (`ChecksumSHA256` param + `x-amz-checksum-sha256` SigV4 signing). When R2 receives bytes whose actual sha256 differs from the value signed in the URL, it rejects with HTTP 400 BadDigest before the bytes are persisted — closing the per-workspace dedup-poisoning gap that Copilot flagged 4× during PR #551 review of #485 Phase 1. The original `generate_presigned_post` proposal in #556 turned out to be non-viable on R2 (returns HTTP 501 NotImplemented for any presigned POST upload); the live integration test `backend/tests/integration/test_r2_live.py` documents that POST limitation in its module docstring and exercises the working PUT mechanism end-to-end. The integrity gate is wired but **DISABLED by default** via `R2_CHECKSUM_BINDING_ENABLED=false`, because enabling the binding makes the SDK's `x-amz-checksum-sha256` request header **required** (older deployed SDKs without it fail with HTTP 403 SignatureDoesNotMatch). **Rollout sequence for self-hosted operators:**
  1. Deploy this backend release with `R2_CHECKSUM_BINDING_ENABLED=false` (default — no behavior change vs. Phase 1).
  2. Update `kagura-memory-python-sdk` to a release that sends the `x-amz-checksum-sha256` header on PUT.
  3. Wait for SDK adoption across tenants — uploads from older SDKs will continue working in the unflipped backend.
  4. Set `R2_CHECKSUM_BINDING_ENABLED=true` to activate the integrity gate.

  The next-major release plans to default the flag true; a follow-up will remove the flag once the SDK floor is widely deployed.
- **Tier-based quota for sleep-enabled contexts** (#560): Sleep Maintenance is now a PRO-only feature with a per-workspace cap on how many contexts can have `sleep_mode != "skip"`. Effective limit = plan tier base + addon: FREE/BASIC = `0 + 0 = 0` (Sleep Maintenance unavailable), PRO = `3 + addon_sleep_contexts_bonus`. The new `extra_sleep_contexts` addon (Stripe SKU is Phase 2 follow-up; the type is wired through `AddonCalculatorService`, `WorkspaceAddon.addon_type` CHECK constraint, and the Pydantic surface so it can sell on day 1). Migration `e06_560` adds `workspaces.addon_sleep_contexts_bonus` and force-skips contexts with `sleep_mode != "skip"` on FREE/BASIC workspaces (one-way; PRO is grandfathered — see `### Notes`). Quota check in `ContextService.update_context` uses an "increase-only" rule: only blocks `skip → full/edges_only` transitions, so PRO workspaces above the limit can naturally taper down by switching contexts back to `skip`. Helper acquires `SELECT ... FOR UPDATE` on the workspace row to serialize concurrent toggles. **API contract**: rejection splits by case — `FeatureNotAvailableError` (HTTP 403, `error_code=FEAT-001`, `feature=sleep_mode`) for FREE/BASIC where the feature is plan-gated, and `QuotaExceededError` (HTTP 429, `error_code=QUOTA-001`, `quota_type=sleep_enabled_contexts`) for PRO at-or-above the cap. Frontend disables `full`/`edges_only` SelectItems in SettingsTabPanel when no headroom is left, and adds a usage card to the workspace dashboard. Motivation: Sleep Maintenance triggers LLM calls per phase, so cost-bearing access needs to track tier/plan. Public Beta launch can size LLM spend predictably.
- **Interactive graph view** (#435): Single-click on a graph node opens `MemoryDetailDialog` (deep-linked via `?memoryId=`, shared with the Memories tab so cross-tab navigation preserves the open memory). Drag-to-reposition is correctly discriminated from click using a 5px squared threshold inside d3-drag's start/end events. Edge click renders a floating metadata overlay (source title, target title, type, weight, optional `created_at` and `confidence`) anchored to the click point; dismissible on Esc / outside-click. Keyboard parity (WCAG 2.1.1): focused nodes activate via Enter/Space. Edge hit area uses a transparent stroke-width=10 line stacked on top of the 1px visual line so users don't need to land precisely on the stroke.
- **Admin-configurable signup gate (Phase 1)** (#358): New `/admin/signup-gate` admin page controls who can register on self-hosted and public instances. Default off preserves existing OSS behavior (`ALLOW_REGISTRATION` env flag continues to control signup). When enabled with mode=`manual`, only GitHub users on the admin-managed allowlist may register; attempts from non-allowlisted accounts redirect to `/signup-blocked`. Matching is on the immutable numeric `github_user_id` (renames don't break the match). Added `signup_gate_config` (singleton) + `signup_allowlist` tables via migration `b04`.

### Changed
- **Default `sleep_mode` for new contexts is now `skip`** (#558): `Context.sleep_mode` `server_default` was flipped from `"full"` to `"skip"` so newly created contexts make no Sleep Maintenance LLM calls until the owner opts in via Settings (#504). The migration is metadata-only (`ALTER COLUMN ... SET DEFAULT`) — existing contexts and rows are unchanged. The Sleep orchestrator's lookup fallback (when `context_id` is missing or DB lookup fails) was also flipped to `"skip"` so an unidentifiable context doesn't burn LLM tokens. The motivation is cost predictability ahead of Public Beta: an opt-in model lets operators reason about LLM spend as signup volume grows.
- **Erasure-request `confirm_token` is now nullable for OAuth users** (#469): `POST /api/v1/me/account/erasure-request` 201 response previously always populated `confirm_token: string`. With this change, OAuth-auth users get `confirm_token: null` (the raw token is delivered via email instead, narrowing the in-band disclosure surface). Password-auth users continue to receive the raw token in-band as the second factor for password re-prompt at confirm time. SDK / client consumers reading `confirm_token` MUST now treat it as `string | null`. Token TTL is 1 hour regardless of delivery channel, so existing mid-flow requests at deploy time will expire within the window. Production `EMAIL_PROVIDER=resend` flip is gated separately on Privacy Policy sub-processor disclosure (#480) and OAuth IdP-side email sync (#481) — code merge of #469 does not flip the channel.
- **Shared-context memory visibility** (#435 follow-up): `GET /api/v1/memory/list?context_id=…` now mirrors the existing graph endpoint pattern (`api/routes/graph.py:159`) — for **shared (non-private) contexts**, every workspace member with read access sees every memory regardless of original creator; for **private contexts**, only the creator continues to see their own memories. Previously the endpoint hard-applied `Memory.user_id == caller`, which meant admin / non-creator team members saw an empty list even after `PermissionService` granted read access. The unscoped "list my memories" path (no `context_id`) is unchanged. Self-hosted operators on team plans should be aware that members of shared contexts will now see each other's memories via the Memories tab UI (the underlying graph view already exposed this).
- **Context detail title icon** (#435 follow-up): The privacy glyph next to the context title now matches the contexts list page — Globe (purple) for public, Lock (blue) for private, Users (green) for shared. Previously the detail page only distinguished private vs non-private, missing the public case and using gray/blue colors.

### Fixed
- **Dev-mode 500 with Next.js 16 + Turbopack** (frontend): `output: "standalone"` in `next.config.ts` is now gated on `NODE_ENV === "production"`. With `next dev` (Turbopack), the unconditional setting caused every request to 500 with `ENOENT: .next/dev/server/app/page/build-manifest.json`. Production Docker builds set `NODE_ENV=production` explicitly in the builder stage so the standalone bundle is still emitted reliably.

### Notes
- **Breaking change for FREE/BASIC users (#560)**: contexts that previously had `sleep_mode = "full"` or `"edges_only"` on FREE/BASIC workspaces are force-skipped during the `e06_560` data migration. These users were never charged for the LLM usage but were generating platform-side cost; the migration brings their behavior in line with the new tier policy. Operator should call this out in the v0.16.0 release notes and consider an in-app banner for FREE/BASIC accounts on first login post-deploy. PRO over-limit users are grandfathered (see `### Added`).
- **`extra_sleep_contexts` addon Stripe SKU**: not yet sold. The addon type is fully wired (`ADDON_UNIT_VALUES`, `WorkspaceAddon` CHECK constraint, `AddonCalculatorService`, `Workspace.addon_sleep_contexts_bonus`, `effective_sleep_enabled_contexts_limit`), so once the Stripe SKU is created and `WorkspaceAddon` rows of this type start appearing, the existing recalculator picks them up. Tracked as a Phase 2 follow-up.
- **Phase 2 follow-up**: GitHub Sponsors sync (`sponsorshipsAsMaintainer` GraphQL cron + `POST /webhooks/github/sponsors` HMAC receiver) and the 6 sponsorship-action state machine are deliberately not yet implemented. Mode selector exposes `github_sponsors` / `both` as disabled options; the PUT update schema is narrowed to `Literal["manual"]` so the backend returns `422` for direct-API calls that set those modes. Table schema already reserves all Sponsors columns so Phase 2 lands without a follow-up migration.
- **Privacy Policy dependency**: before enabling this gate on any hosted deployment, Privacy Policy must document allowlist retention + revocation flow. Tracked under #359 (`docs(legal): Privacy Policy / ToS / Cookie Policy draft`) — ship together per the v0.14.0 Access + Legal bundle rule.

## [v0.12.0](https://github.com/kagura-ai/memory-cloud/releases/tag/v0.12.0) — 2026-04-16

### Highlights

The Resource Foundation refactor (epic #321) normalizes the resource subsystem around a new `resources` entity with UUID primary keys, enforces cross-tenant isolation at both the database and API layers, and maintains full backward compatibility for all external API contracts (REST and MCP). See [`docs/resource-foundation-migration.md`](docs/resource-foundation-migration.md) for the self-hosted migration guide.

### Security
- **Critical (OWASP A01 / CWE-639)**: Fixed cross-tenant memory injection via Resource Ingest API (#322, parent epic #321). All self-hosted deployments with Resource Ingest enabled must upgrade. See `SECURITY.md` for the advisory and upgrade steps.

### Added
- **Resources entity** (#323): New `resources` table (UUID PK, workspace FK) as the authoritative source of truth for resource identity. Satellite tables (`resource_events`, `resource_schemas`, `indexer_state`, `resource_tokens`) gain `resource_pk` UUID FK columns with backfill from existing data.
- **API compatibility shim** (#326): `PermissionService.resolve_resource_by_slug()` translates incoming `resource_id` slugs to internal UUIDs with workspace boundary enforcement. External API URLs remain unchanged.
- **Resource Indexer API** (#326): `GET /api/v1/resources/{resource_id}/indexer-status` endpoint for monitoring indexer progress per resource.

### Fixed
- **Resource indexer per-context EmbeddingService selection** (#338): After #334 routed per-context Qdrant collections, `_apply_upsert` still called `EmbeddingService` with the global default model, so contexts using e.g. `qwen3-embedding:8b` (4096 dim) had upserts rejected on dim mismatch against the 4096-dim collection. The per-batch routing helper now resolves `(collection_name, embedding_service)` from a single `ContextSearchConfig` fetch (`_resolve_routing_for_context`) so both values come from the same config. Falls back to the legacy `kagura_memories` collection + the indexer's default `EmbeddingService` when no `ContextSearchConfig` row exists — matching `memory_service` exactly, so both services keep reading/writing the same collection for legacy contexts. Operators overriding `settings.embedding_model` must create a `ContextSearchConfig` row per context to opt into the per-context routing path.
- **Resource indexer per-context collection routing** (#334): `resource_indexer` was hardcoding the legacy `kagura_memories` (512-dim) collection at every Qdrant call site, so any context configured with a non-default embedding model (e.g. `qwen3-embedding:8b` → 4096 dim) would have its upserts rejected by Qdrant on dim mismatch. The indexer now resolves the per-context collection via `get_collection_name(model, dimensions)` from `ContextSearchConfig`, mirroring the existing `memory_service` pattern. Falls back to legacy `kagura_memories` when no `ContextSearchConfig` row exists. Layer C (per-context `EmbeddingService` selection) is addressed by #338.
- **Resource indexer Qdrant upsert** (#324): Resource ingest events were silently failing at the Qdrant write path with `"Not existing vector name error"` because the indexer upserted anonymous vectors into a named-vector collection (`dense` + sparse `bm25`). Fixed by switching to `PointStruct(vector={"dense": embedding})` and unmasked a latent `Memory(collection_name=...)` kwarg error left over from the Single Collection Migration. See `docs/ops/resource-indexer-backfill.md` for re-queue procedure for stuck `indexer_state` rows.

### Database
- Added migration `a96`: global partial UNIQUE index `ux_contexts_resource_id_active` on `contexts(resource_id)` for active rows. Zero-downtime (`CREATE INDEX CONCURRENTLY`). Aborts if pre-existing cross-workspace `resource_id` collisions are detected — operators must resolve duplicates before upgrading.
- Added migration `a97`: `resources` entity table, `resource_pk` UUID FK on satellite tables with backfill, `resource_tokens.workspace_id` shadow FK, and three partial UNIQUE indexes. Includes pre-flight audits for orphan rows and cross-workspace ambiguity.

### Documentation
- Added `docs/resource-foundation-migration.md`: self-hosted migration guide with prerequisites, step-by-step instructions, rollback procedures, and API compatibility details.
- Updated `SECURITY.md`: strengthened upgrade recommendation for self-hosted operators.
