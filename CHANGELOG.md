## [v0.71.0](https://github.com/kagura-ai/memory-cloud/releases/tag/v0.71.0) — 2026-09-20

Operational hygiene for the single-server template: bounded container logs, and proxy logs that never hold an invite token.

### Fixed
- **Container logs are bounded** ([#1591](https://github.com/kagura-ai/memory-cloud/issues/1591)): every service in `terraform/single-server/docker-compose.app.yml`, `docker-compose.prod.yml`, `docker-compose.data.yml` and `docker-compose.ollama.yml` declares `logging: json-file` with `max-size: 50m` / `max-file: 3` through a per-file `x-logging` anchor. A host that was not provisioned with a Docker `daemon.json` no longer lets the proxy's JSON access log grow until the disk fills. The options take effect when a container is (re)created.
- **The Caddy template scrubs invite tokens from its logs** ([#1591](https://github.com/kagura-ai/memory-cloud/issues/1591)): `Caddyfile.tpl` logs through a `filter` encoder that replaces the token slot of `/join/<token>`, `/beta-invites/<token>/preview` and `invite=<token>` with `REDACTED` in `request>uri` and in the `Location` / `Refresh` response headers (a trailing-slash redirect echoes the path), and drops the `Referer`, `Cookie`, `Next-Url` and `Next-Router-State-Tree` request headers. The same scrub is applied to Caddy's **default logger**: when an upstream is down, Caddy writes a second `http.log.error` line about the request to stderr with the full URI and headers, so filtering the access log alone left a copy of the token in the same container log. Ordinary URIs are logged unchanged.

### Notes
- **Applying to a running stack:** re-render the Caddyfile and reload Caddy for the log format (no recreate needed). For rotation, run `docker compose … up -d --force-recreate caddy web` once — the API colours are recreated by every `deploy.sh` run; recreating a container also discards its old oversized log file; `postgres` / `qdrant` / `redis` restart when recreated, so do that in a maintenance window. A host-level `daemon.json` with the same limits remains a good default.
- **Caddy 2.6.2+** is required for the response-header redaction (an older 2.x image silently skips it; the URI rewrite and the header deletes still work) — `docker compose pull caddy`.
- No application code, API, migration or environment-variable change. With this template the proxy-log precondition for `ENABLE_BETA_INVITES` (see v0.70.0) is met out of the box; if you run a different proxy, replicate the scrub for both its access log and its error log. See Deployment → *Container log rotation* and *Closed-beta invite links*.
- Two new bats suites (static pins, and a live suite against `caddy:2-alpine` including the 502 path) run in the CI `shell` job.

## [v0.70.0](https://github.com/kagura-ai/memory-cloud/releases/tag/v0.70.0) — 2026-09-19

Closed-beta invite links, an admin environment console that tells the truth, and a sharing gate that no longer blocks unrelated context edits.

### Added
- **Closed-beta invite links** ([#1581](https://github.com/kagura-ai/memory-cloud/issues/1581), [#1582](https://github.com/kagura-ai/memory-cloud/issues/1582)): with `ENABLE_BETA_INVITES=true` a signed-in user mints one-time `/join/{token}` links (7-day TTL) that let one new person through a closed signup gate. Each user holds up to `BETA_INVITE_QUOTA_PER_USER` invites (default 4, counting active + redeemed; expired and revoked invites free their slot; system admins are uncapped). Only the SHA-256 of the token is stored and the URL is returned once. Redemption happens at the OAuth callback, only where the gate would otherwise block, and records the invitee in `signup_allowlist` as `source='beta_invite'` keyed on the immutable IdP identity (never the e-mail, [#655](https://github.com/kagura-ai/memory-cloud/issues/655)) and attributed to the inviter. API: `GET /api/v1/beta-invites/me`, `POST /api/v1/beta-invites`, `DELETE /api/v1/beta-invites/{id}`, public `GET /api/v1/beta-invites/{token}/preview` (per-IP rate limited), `invite=` on `GET /api/v1/auth/{provider}/login`; `features.beta_invites` on `/system/info`. The inviter sees status only (`active` / `redeemed` / `expired` / `revoked`), never the invitee.
- **Invite UI** ([#1582](https://github.com/kagura-ai/memory-cloud/issues/1582)): an "Invite a friend" card above the account menu (dismissable, hidden at the cap), a permanent account-menu entry with the `n/4` counter, a dialog that shows the link once with Copy and lists/revokes invites, and the public `/join/[token]` landing page. `/signup-blocked` points invitees back to their link. Nothing renders and nothing is requested while the flag is off or unknown.
- **`/join/*` sends no `Referer` and is not indexed** ([#1588](https://github.com/kagura-ai/memory-cloud/issues/1588)): the landing route is served with `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex, nofollow`, repeated as `<meta>` tags for deployments whose proxy overwrites response headers, so the invite token is not copied into a header that proxies log.
- **Invite tokens are scrubbed from logs and `usage_stats`** ([#1581](https://github.com/kagura-ai/memory-cloud/issues/1581)): structlog events, the stdlib / uvicorn access log and the persisted request path show the literal `{token}` for the three invite URL shapes.
- **Hosted-mode settings in the admin environment console** ([#1580](https://github.com/kagura-ai/memory-cloud/issues/1580)): system admins see a read-only `hosted` category (`ENABLE_BYOK`, `RESOLVE_STORED_BYOK_KEYS`, `ENABLE_COST_DISPLAY`, `MANAGED_LLM_*`, `DEFAULT_RERANKER_*` / `DEFAULT_USE_RERANK`, `RERANK_BASE_URL` with credentials masked, `RERANK_MODEL`, `ENABLE_PLAN_PAGE`). Non-admin callers of `GET /config` see the same keys as before.

### Changed
- **`/admin/environment` is read-only and shows effective values** ([#1580](https://github.com/kagura-ai/memory-cloud/issues/1580)): `GET /api/v1/config` renders what `get_settings()` actually uses (items gain `read_only: true`); `PUT /api/v1/config/{key}` and `POST /api/v1/config/batch` answer **409 `CFG-002`** instead of 200. Values saved from that page were never read by any runtime consumer, so existing `config_overrides` rows were never effective and are now ignored (no migration; the table stays for account-erasure pseudonymisation). Env-only Neural Memory flags (`TRACK_CO_ACTIVATION`, `ENABLE_DECAY`, `ENABLE_TRUST_MODULATION`) now display their effective default instead of "Disabled".
- **The reranker card is hidden when the deployment does not rerank** ([#1580](https://github.com/kagura-ai/memory-cloud/issues/1580)): with `features.reranking=false` the context search settings render no reranker card and make no external-keys request (v0.69.0 showed it disabled with a note). Unknown / still-loading keeps the card.
- **The shared-context gate fires only on the private → shared transition** ([#1583](https://github.com/kagura-ai/memory-cloud/issues/1583)): `PUT /contexts/{id}` with a no-op `is_private: false` on an already-shared context is accepted on a plan without `shared_contexts` (block-new-only, same rule as `is_public`), so unrelated edits such as `sleep_mode` are no longer refused. The Settings tab sends only fields the user touched, disables "Make shared" with an explanation on plans without the feature, and names the control in a FEAT-001 toast.
- **Feature-refusal text uses display names on both sides** ([#1583](https://github.com/kagura-ai/memory-cloud/issues/1583)): "… not available on M plan. Upgrade to L plan …" instead of mixing the raw plan key with the display name. `details.feature` is unchanged.

### Notes
- **Migration:** `alembic upgrade head` — `e82_1581_beta_invites` (new `beta_invites` table; `signup_allowlist.source` CHECK admits `beta_invite`). Downgrade refuses while `beta_invite` allowlist rows exist.
- **New env knobs:** `ENABLE_BETA_INVITES` (default `false` — also the kill switch for minting *and* redemption), `BETA_INVITE_QUOTA_PER_USER` (default `4`, `0` = system admins only). See Deployment → *Closed-beta invite links*.
- **Before enabling invites behind a reverse proxy that writes access logs:** the proxy records the request URI and the `Referer` header, both of which carry the invite token on `/join/{token}`. Scrub those fields or restrict access to the logs first; the application's own logs are already scrubbed, and current browsers send no `Referer` from `/join/*` ([#1588](https://github.com/kagura-ai/memory-cloud/issues/1588)), which leaves the URI as the field that must be filtered.
- **New error codes:** `CFG-002` (409, read-only configuration), `BETA-INVITE-001` (409, quota exceeded) and `BETA-INVITE-002` (409, already redeemed). New audit actions `beta_invite.created` / `.redeemed` / `.revoked`.

## [v0.69.0](https://github.com/kagura-ai/memory-cloud/releases/tag/v0.69.0) — 2026-09-19

Hosted mode without BYOK: platform-managed reranking, Analysis and Sleep, operator pricing for paid OpenAI-compatible endpoints, and UI gates for money surfaces.

### Added
- **Operator pricing overrides** ([#1570](https://github.com/kagura-ai/memory-cloud/issues/1570)): `LLM_PRICING_OVERRIDES` (JSON array of `{provider, model, unit_type, price_per_unit[, unit_denominator][, context_min_tokens]}`, USD) is validated at boot and appended to `llm_pricing` at API startup when the effective price differs (append-only, cache cleared); `python -m src.cli.sync_llm_pricing [--plan|--apply]` re-syncs without a restart.
- **Reranking as a deployment default** ([#1572](https://github.com/kagura-ai/memory-cloud/issues/1572)): `DEFAULT_RERANKER_PROVIDER` / `DEFAULT_USE_RERANK` / `DEFAULT_RERANKER_MODEL` seed every new or lazily-materialized context search config; with `self_hosted` + `RERANK_BASE_URL` reranking needs no per-workspace key. `GET /api/v1/system/info` exposes `features.reranking` and `search_defaults`; `python -m src.cli.apply_rerank_defaults (--workspace | --all) [--plan|--apply]` converts existing default-valued contexts.
- **Managed LLM lane** ([#1569](https://github.com/kagura-ai/memory-cloud/issues/1569)): `MANAGED_LLM_PROVIDER` (`openai` | `anthropic` | `gemini` | `self_hosted`) + `MANAGED_LLM_MODEL` let Memory Analysis run with zero workspace keys (`paid_by='platform'`, single model, platform credential only) for plans carrying the new `managed_llm` feature (L / XL by default, overridable via `PLAN_<KEY>_FEATURES`); Sleep's judge defaults to the same pair when `SLEEP_LLM_*` is unset. `features.managed_llm` on `/system/info`; `managed_llm` row on the plan matrix.
- **`RESOLVE_STORED_BYOK_KEYS`** ([#1569](https://github.com/kagura-ai/memory-cloud/issues/1569)): opt-in (`false`, requires `ENABLE_BYOK=false`) that makes the LLM, embedding and reranker services ignore stored `external_api_keys` rows, so "BYOK off" can mean off.
- **`ENABLE_COST_DISPLAY`** ([#1571](https://github.com/kagura-ai/memory-cloud/issues/1571), default `true`): when `false` the workspace cost dashboard answers 404, REST analysis cost fields are `null`, MCP analysis payloads omit the cost keys and the web UI shows no `$` to workspace users. `/admin/cost` and `GET /admin/cost-aggregation` are unaffected.
- **Sidebar Resources / Connectors gated by plan + presence** ([#1571](https://github.com/kagura-ai/memory-cloud/issues/1571)): the entries appear when the plan carries the feature or the workspace already owns such objects (one lazy list probe per workspace per session on lower tiers); existing objects keep working ([#1551](https://github.com/kagura-ai/memory-cloud/issues/1551)).
- `self_hosted` chat completions honour `SELF_HOSTED_MODEL_ALIASES`, retry once without `response_format` when the server rejects it, and read `SELF_HOSTED_LLM_TIMEOUT_SECONDS` ([#1569](https://github.com/kagura-ai/memory-cloud/issues/1569)). `SLEEP_LLM_PROVIDER` accepts `anthropic` and `gemini`.

### Changed
- **Context-level `use_rerank` applies when the caller omits the flag** ([#1572](https://github.com/kagura-ai/memory-cloud/issues/1572)): `RecallRequest.use_rerank` and the MCP `recall` argument are tri-state — omitted follows the context's search config; explicit `true` / `false` behaves as before. Existing contexts default to `false`, so only contexts whose owner enabled reranking change behaviour.
- **`ENABLE_RERANKING` is now a real deployment kill switch** ([#1572](https://github.com/kagura-ai/memory-cloud/issues/1572)); it was read nowhere before. Default `true` (the `.env.example` value was corrected from `false`).
- **`self_hosted` embeddings are spend-capped iff their effective price is above zero** ([#1570](https://github.com/kagura-ai/memory-cloud/issues/1570)): a priced self-hosted model gets `PLAN_<KEY>_EMBEDDING_*_CAP_USD`, the per-workspace override, the 80 % / 100 % owner mails and `QUOTA-002` on every tier; unpriced stays uncapped.
- **Unknown price renders as `—`, not `$0.00`** ([#1570](https://github.com/kagura-ai/memory-cloud/issues/1570)): migration `e80` removes the seeded `$0` rows for the five `self_hosted` embedding models (FK-referenced rows kept). Set an override at price `0` to get `$0.00` back for a truly free local model.
- **Analysis estimate and actual cost read the same pricing snapshot** ([#1570](https://github.com/kagura-ai/memory-cloud/issues/1570)): `estimated_cost_cents` (REST preview, MCP `analyze_context(dry_run=true)`) and `cost_estimated_cents` / `cost_actual_cents` are `null` when the model is unpriced instead of a hardcoded guess or a 500. An unpriced managed-lane run records `model_id = NULL` plus new `llm_provider` / `llm_model` columns (migration `e81`, [#1569](https://github.com/kagura-ai/memory-cloud/issues/1569)).
- **Reranker fail-open is visible** ([#1572](https://github.com/kagura-ai/memory-cloud/issues/1572)): a fully failed `self_hosted` scoring batch now degrades to un-reranked hybrid results with a `rerank_failed_open` warning instead of silently returning arbitrary order. New contexts write `reranker_model=rerank-2` (was `rerank-2-lite` on one path).
- Analysis VAL-001 refusal text names both routes (workspace OpenAI key, or the deployment's managed lane + `managed_llm` feature); a caller-pinned pricing `model_id` is refused (422) on the managed lane ([#1569](https://github.com/kagura-ai/memory-cloud/issues/1569)).
- The web UI reranker card shows the deployment's actual default and is disabled with a note when `features.reranking` is `false` ([#1572](https://github.com/kagura-ai/memory-cloud/issues/1572)).

### Notes
- **Migrations:** `alembic upgrade head` — `e80_1570` (delete seeded `$0` self_hosted pricing rows) and `e81_1569` (`memory_analyses.model_id` nullable, `llm_provider` / `llm_model` columns). `e81` downgrade refuses while unpriced (NULL `model_id`) runs exist.
- **New env knobs:** `LLM_PRICING_OVERRIDES`; `DEFAULT_RERANKER_PROVIDER` / `DEFAULT_USE_RERANK` / `DEFAULT_RERANKER_MODEL`; `MANAGED_LLM_PROVIDER` / `MANAGED_LLM_MODEL`; `RESOLVE_STORED_BYOK_KEYS`; `SELF_HOSTED_LLM_TIMEOUT_SECONDS`; `ENABLE_COST_DISPLAY`. `ENABLE_RERANKING` and the `RERANK_BASE_URL` / `RERANK_MODEL` / `RERANK_API_KEY` / `SELF_HOSTED_RERANK_MODEL` family are now documented. Half-configured lanes or malformed overrides refuse to start the API, naming the variable. See Deployment → *LLM & Embedding Pricing*, *Reranking*, *LLM Credentials* and *Hosted-mode UI gates*.
- **New log events:** `llm_pricing_override_applied` / `llm_pricing_overrides_synced` / `llm_pricing_overrides_sync_failed`, `rerank_failed_open`, `analysis_managed_model_unpriced`, `sleep_llm_from_managed_lane`, `byok_key_resolution_disabled`, `self_hosted_response_format_unsupported`.

## [v0.68.0](https://github.com/kagura-ai/memory-cloud/releases/tag/v0.68.0) — 2026-09-19

The four-tier plan matrix ([#1547](https://github.com/kagura-ai/memory-cloud/issues/1547)).

### Added
- **XL (`promax`) tier** ([#1547](https://github.com/kagura-ai/memory-cloud/issues/1547), [#1551](https://github.com/kagura-ai/memory-cloud/issues/1551)): a fourth plan above L (`pro`). Tiers are S / M / L / XL (`free` / `basic` / `pro` / `promax`); display names remain env-overridable.
- **Owned-workspace cap by plan** ([#1550](https://github.com/kagura-ai/memory-cloud/issues/1550)): a user may own **1 / 1 / 3 / 20** workspaces on S / M / L / XL (`owned_workspace_grant`). Existing workspaces above the cap are kept — only creation is gated.
- **Daily memory-creation quota `memories_per_day`** ([#1549](https://github.com/kagura-ai/memory-cloud/issues/1549)): memories created per workspace per UTC day — **50 / 300 / 2,000 / 10,000** by default (`0` means none, not unlimited). The Redis counter fails open and is observable via structured logs ([#1556](https://github.com/kagura-ai/memory-cloud/issues/1556)).
- **`PLAN_<KEY>_FEATURES` env override** ([#1559](https://github.com/kagura-ai/memory-cloud/issues/1559)): a self-hosted deployment can re-enable `resources` / `connectors` / `public_contexts` (or any feature) on a lower tier; unknown names and invariant violations (`resources` ⊆ `public_contexts`, `secret_store` everywhere) are rejected at startup and `FEATURE_MIN_PLANS` follows the effective tiers.
- **Blocking Redis pool** ([#1556](https://github.com/kagura-ai/memory-cloud/issues/1556)): `REDIS_MAX_CONNECTIONS` (50) / `REDIS_POOL_TIMEOUT_SECONDS` (2.0); pool exhaustion no longer turns the daily quotas fail-open silently — every fail-open emits `quota_check_failed_open`.
- **Admin add-on warning** ([#1561](https://github.com/kagura-ai/memory-cloud/issues/1561)): `PUT /api/v1/admin/plans/workspaces/{id}/quotas` now returns `warnings` (e.g. `["connectors_feature_missing"]`) when `extra_connectors` seats are granted to a tier without the `connectors` feature. The grant is stored — admins may pre-grant ahead of an upgrade — but stays inert until the workspace is upgraded; the admin UI shows the warning in the add-on dialog.

### Changed
- **L (`pro`) can no longer create public contexts, resources or connectors** ([#1551](https://github.com/kagura-ai/memory-cloud/issues/1551)): `setup_resource`, new resource tokens, `setup_connector` and the private→public context transition require the `resources` / `connectors` / `public_contexts` feature, which only XL carries by default. **This blocks new creation only — existing public contexts, resource tokens and connectors on L keep working** (listed, served, editable, ingesting). The M/L token and connector caps now bound only what those plans already hold.
- **Unified feature-refusal text** ([#1561](https://github.com/kagura-ai/memory-cloud/issues/1561)): the plan-feature gates for `connectors`, `resources`, `public_contexts`, `QuotaService.check_feature_access` and the REST shared-context routes now build their FEAT-001 refusal via `FeatureNotAvailableError.for_feature`, which derives the tier name from the plan registry and always sets `details.feature`. The REST shared-context gates (create and update) answer FEAT-001 (403) with that text instead of fixed "Pro plan" wording; the update path previously answered 400. The analysis and sleep gates keep their own wording.
- **Frontend create gates and token caps come from the plan API** ([#1560](https://github.com/kagura-ai/memory-cloud/issues/1560)): `usePlanFeatures` reads the tier booleans and `GET /workspaces/{id}/plan` quotas instead of hard-coded tier names; the plan page separates "what each plan can create" from the workspace's current entitlements.
- **Legacy tier enums removed** ([#1553](https://github.com/kagura-ai/memory-cloud/issues/1553)): `UserPlan` / `RETENTION_BY_PLAN`.
- Docs swept for stale "Pro plan" creation claims — `mcp-tools`, `resource-tokens-guide`, `api-surface-1.0/mcp-input-schemas`, `connector-ingest-contract` ([#1561](https://github.com/kagura-ai/memory-cloud/issues/1561)).

### Notes
- **Billing:** the billing side must map a `promax` SKU before XL can be sold self-serve; until then XL is admin-assigned. Existing L subscriptions are not migrated automatically.
- **New env knobs:** `PLAN_PROMAX_*` (numeric limits and display name for the new tier), `PLAN_<KEY>_MEMORIES_PER_DAY` and `PLAN_<KEY>_OWNED_WORKSPACE_GRANT` for every tier key. `PLAN_<KEY>_FEATURES` overrides a tier's feature set ([#1559](https://github.com/kagura-ai/memory-cloud/issues/1559)); `REDIS_MAX_CONNECTIONS` / `REDIS_POOL_TIMEOUT_SECONDS` size the Redis pool ([#1556](https://github.com/kagura-ai/memory-cloud/issues/1556)). See [Deployment → Plan Tiers](docs/deployment.md#plan-tiers).

## Historical development notes (pre-v0.16.0)

### Added
- **Embedded LanceDB vector backend — "Kagura Lite" (preview)**: a feature-flagged, in-process vector store for single-process self-hosted / CLI / desktop / edge deployments that want to avoid running a separate Qdrant server. Set `KAGURA_VECTOR_BACKEND=lance` (default `qdrant` is unchanged — the new path is a single `is None` branch in `db/qdrant.py`, zero behavior change for the server). New `db/vector_store.py` introduces a `VectorStore` Protocol + cached backend selector; `db/lance_store.py` implements `LanceVectorStore`. Japanese stays owned by the existing Sudachi pipeline (lemmas + readings + synonym/hiragana augmentation) feeding a weighted `search_text` FTS column, so recall behavior matches the Qdrant path without relying on LanceDB's native CJK tokenizer; hybrid 60/40 fusion stays in `services/search_service.py`. Unit-tested: backend selector + the security-critical filter/escaping builder (LanceDB-independent). **Post-merge hardening (max code-review follow-up):** semantic search now sets `.metric("cosine")` explicitly (LanceDB defaulted to L2 → wrong/negative similarity scores that broke confidence/absence detection); all writes serialized under the store lock (LanceDB is single-writer even in-process); embedding dimension tracked per-collection (multi-model variants no longer collide); date-range filters normalized to canonical UTC (offset-aware, validated); FTS + scalar indexes rebuilt lazily after the first write; importance-range consistency validated (4xx parity with Qdrant); reads/deletes on a not-yet-created collection return empty instead of erroring.
- **Slot-based owned-workspace cap (epic #674)**: User-level workspace ownership is now gated by `cap = 1 (base) + users.workspace_slot_bonus`, decoupling the cap from workspace plan tier (FREE/BASIC/PRO). The two axes are now orthogonal — `workspace.plan` controls feature limits (memory / api), `users.workspace_slot_bonus` controls how many workspaces a user may own. **Phase 1 ship breakdown:**
  - **Data model + cap rewrite** (#675 sub-A): alembic `e15_675_workspace_slot_bonus` adds `users.workspace_slot_bonus INTEGER NOT NULL DEFAULT 0` with a `>= 0` CHECK constraint. `QuotaService.check_workspace_creation_allowed` switched from highest-tier derivation to `BASE_CAP + bonus`. `PlanTier.max_owned_workspaces` field removed.
  - **Admin inc/dec UI** (#676 sub-B, supersedes #667): new `PATCH /api/v1/admin/users/{user_id}/workspace_slot_bonus` endpoint (atomic `UPDATE ... RETURNING` for race safety, DB CHECK as safety net, `BONUS-002` structured 400 for would-be-negative requests, audit log on every mutation, `reason` required only when the new cap would drop below current owned_count). The full detail route `/admin/users/{user_id}` surfaces the bonus value with `+1` / `−1` buttons.
  - **TOCTOU + enforce flip** (#677 sub-C): `QuotaService._acquire_workspace_create_lock` uses `pg_advisory_xact_lock(hashtextextended('workspace_create:' || user_id, 0))` (64-bit hash, per-user serialization, released on transaction commit, zero contention with other paths). The 64-bit `hashtextextended` was deliberately chosen over 32-bit `hashtext` to push birthday-paradox collisions from ~65k users out to ~2³² users (PR #686 loop 4 review). The `ENFORCE_WORKSPACE_CAP` flag flips warn-only → deny + `QuotaExceededError` 4xx. Production `memory.kagura-ai.com` flipped to `true` on 2026-05-17 (rollback runbook: `docs/ops/workspace-cap-rollback.md`).
  - **Cap visibility on admin list** (#695): `/admin/users` list response gains `owned_count` / `workspace_slot_bonus` / `base_cap` / `cap` per user (additive — mirrors `WorkspaceSummary` field names from the detail endpoint, so client code and mental models stay consistent across closely-related admin endpoints). The list page renders a new "Cap" column with at-cap emphasis and a bonus-inclusive tooltip.
  - **Tiers docs update** (#664): admin `/plans` "Tiers" tab no longer surfaces a `max_owned_workspaces` column (the value was removed from `PlanTier`).

  **Migration safety**: the grandfather migration uses `EXCLUSIVE TABLE LOCK` on `users` for the brief window of `UPDATE users SET workspace_slot_bonus = GREATEST(0, owned_count - 1)` — existing PRO users with N owned workspaces keep their effective cap (bonus = N − 1). **Idempotent**: re-running the migration converges to the same value (`GREATEST(0, count - 1)`).

  **Self-hosted operators**: `terraform/single-server/.env.prod.example` documents `ENFORCE_WORKSPACE_CAP=true` as the recommended default once log-only observation confirms no false-positive denials. The rollback runbook documents service-name-explicit `--force-recreate` recovery without redeploy.

  **Phase 2 follow-up (not in this release)**: Stripe "workspace slot" product / webhook-driven bonus increment / dangling-workspace handling. The Phase 1 model is intentionally local-only; the Phase 2 design will upgrade `workspace_slot_bonus` from a raw column to a SUM cache backed by `UserSlotPurchase` rows so the addon pattern (#485 storage_limit etc.) carries through cleanly.

### Added
- **Body sha256 binding on presigned PUT (Phase 1.5)** (#556): `R2Storage.generate_presigned_put` now plumbs the reserved `sha256` through to R2's S3 Object Integrity feature (`ChecksumSHA256` param + `x-amz-checksum-sha256` SigV4 signing). When R2 receives bytes whose actual sha256 differs from the value signed in the URL, it rejects with HTTP 400 BadDigest before the bytes are persisted — closing the per-workspace dedup-poisoning gap that Copilot flagged 4× during PR #551 review of #485 Phase 1. The original `generate_presigned_post` proposal in #556 turned out to be non-viable on R2 (returns HTTP 501 NotImplemented for any presigned POST upload); the live integration test `backend/tests/integration/test_r2_live.py` documents that POST limitation in its module docstring and exercises the working PUT mechanism end-to-end. The integrity gate is wired but **DISABLED by default** via `R2_CHECKSUM_BINDING_ENABLED=false`, because enabling the binding makes the SDK's `x-amz-checksum-sha256` request header **required** (older deployed SDKs without it fail with HTTP 403 SignatureDoesNotMatch). **Rollout sequence for self-hosted operators:**
  1. Deploy this backend release with `R2_CHECKSUM_BINDING_ENABLED=false` (default — no behavior change vs. Phase 1).
  2. Update `kagura-memory-python-sdk` to a release that sends the `x-amz-checksum-sha256` header on PUT.
  3. Wait for SDK adoption across tenants — uploads from older SDKs will continue working in the unflipped backend.
  4. Set `R2_CHECKSUM_BINDING_ENABLED=true` to activate the integrity gate.

## [v0.12.0](https://github.com/kagura-ai/memory-cloud/releases/tag/v0.12.0) — 2026-04-16

### Highlights

The Resource Foundation refactor (epic #321) normalizes the resource subsystem around a new `resources` entity with UUID primary keys, enforces cross-tenant isolation at both the database and API layers, and maintains full backward compatibility for all external API contracts (REST and MCP). See [`docs/resource-foundation-migration.md`](docs/resource-foundation-migration.md) for the self-hosted migration guide.

### Security
- **Critical (OWASP A01 / CWE-639)**: Fixed cross-tenant memory injection via Resource Ingest API (#322, parent epic #321). All self-hosted deployments with Resource Ingest enabled must upgrade. See `SECURITY.md` for the advisory and upgrade steps.

### Added
- **Resources entity** (#323): New `resources` table (UUID PK, workspace FK) as the authoritative source of truth for resource identity. Satellite tables (`resource_events`, `resource_schemas`, `indexer_state`, `resource_tokens`) gain `resource_pk` UUID FK columns with backfill from existing data.
- **API compatibility shim** (#326): `PermissionService.resolve_resource_by_slug()` translates incoming `resource_id` slugs to internal UUIDs with workspace boundary enforcement. External API URLs remain unchanged.
- **Resource Indexer API** (#326): `GET /api/v1/resources/{resource_id}/indexer-status` endpoint for monitoring indexer progress per resource.

### Fixed
- **Resource indexer per-context EmbeddingService selection** (#338): After #334 routed per-context Qdrant collections, `_apply_upsert` still called `EmbeddingService` with the global default model, so contexts using e.g. `qwen3-embedding:8b` (4096 dim) had upserts rejected on dim mismatch against the 4096-dim collection. The per-batch routing helper now resolves `(collection_name, embedding_service)` from a single `ContextSearchConfig` fetch (`_resolve_routing_for_context`) so both values come from the same config. Falls back to the legacy `kagura_memories` collection + the indexer's default `EmbeddingService` when no `ContextSearchConfig` row exists — matching `memory_service` exactly, so both services keep reading/writing the same collection for legacy contexts. Operators overriding `settings.embedding_model` must create a `ContextSearchConfig` row per context to opt into the per-context routing path.
- **Resource indexer per-context collection routing** (#334): `resource_indexer` was hardcoding the legacy `kagura_memories` (512-dim) collection at every Qdrant call site, so any context configured with a non-default embedding model (e.g. `qwen3-embedding:8b` → 4096 dim) would have its upserts rejected by Qdrant on dim mismatch. The indexer now resolves the per-context collection via `get_collection_name(model, dimensions)` from `ContextSearchConfig`, mirroring the existing `memory_service` pattern. Falls back to legacy `kagura_memories` when no `ContextSearchConfig` row exists. Layer C (per-context `EmbeddingService` selection) is addressed by #338.
- **Resource indexer Qdrant upsert** (#324): Resource ingest events were silently failing at the Qdrant write path with `"Not existing vector name error"` because the indexer upserted anonymous vectors into a named-vector collection (`dense` + sparse `bm25`). Fixed by switching to `PointStruct(vector={"dense": embedding})` and unmasked a latent `Memory(collection_name=...)` kwarg error left over from the Single Collection Migration. See `docs/ops/resource-indexer-backfill.md` for re-queue procedure for stuck `indexer_state` rows.

### Database
